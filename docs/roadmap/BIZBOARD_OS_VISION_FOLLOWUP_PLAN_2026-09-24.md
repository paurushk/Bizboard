## W2. Regenerate the OpenAPI snapshot

**Gap.** CI runs `python manage.py spectacular --format openapi-json --file ../docs/openapi-snapshot.json` and then `git diff --exit-code docs/openapi-snapshot.json`. The frontend job runs `npm run gen:api-types` and diffs `web/src/api/openapi-types.ts`. Endpoints and fields added after the last successful generate are absent from both files, so CI will report drift.

**Do not hand-edit either file.**

**Check the interpreter before assuming CI has to do this.** Run `python -c "import sys; print(sys.version)"`. If the version string contains `free-threading`, or the executable is `python3.13t`, `spectacular` fails importing `rpds.rpds`, and rebuilding `rpds-py` fails because PyO3 does not support free-threaded CPython below 3.14. Do not retry that Rust build. On that interpreter, leave the generate to CI or to a standard CPython 3.13.

A standard CPython 3.13 (GIL enabled) can import `config.urls` and `rpds.rpds`. On that interpreter, run the two commands in this workspace. Do not defer them to CI just because an earlier session was on the free-threaded build.

**How to generate.** From `backend/` with `DJANGO_SETTINGS_MODULE=config.settings_test` and the dev requirements installed:

```
python manage.py spectacular --format openapi-json --file ../docs/openapi-snapshot.json
```

Then from `web/`:

```
npm run gen:api-types
```

Commit both generated files together. Run W1 first so the new webhook-token action is in the schema.

## W3. Postgres race tests for the locks already in place

**Gap.** `sales/order_gates.py` locks the customer row inside `apply_order_gates`, and `accounts/packs.py` locks the company and `CompanyPackState` inside `apply_pack`. SQLite does not serialize `select_for_update()`, so a race test here would pass without proving the lock. CI does run Postgres. The existing pattern is `backend/tests/test_concurrency_races.py`: `pytest.mark.postgres`, `pytest.mark.django_db(transaction=True)`, and skip unless `connection.vendor == "postgresql"`.

**Tests.** Add two tests in that file, or in a sibling file that uses the same marks and the same skip. Both are pure races between two different rows or two overlapping applies. Leave the existing sequential hand-edit coverage where it is: `test_pack_confirm_does_not_overwrite_a_manual_deviation` in `test_os_vision_plan.py` and `test_pack_adds_four_flags_and_does_not_rewrite_a_hand_edit` in `test_onboarding.py`. A barrier-released pair of identical calls has no window for a hand edit to land between them, so that scenario does not belong in the race test.

- **Two different sales orders, one customer.** Create two `SalesOrder` rows for the same customer. Set the credit limit large enough for one order's `grand_total` and too small for both. Release both `confirm_sales_order` calls together. One confirm succeeds. The other raises `credit_limit_exceeded`. Both must not succeed. Do not race the same order twice. `confirm_sales_order` already locks that order row (`SalesOrder.objects.select_for_update().get(pk=order.pk)`), so two calls on one order serialize on the order lock and never reach the customer-exposure lock this test is there to prove.
- **Two concurrent pack applies, one company.** Release two `apply_pack` calls for the same company and the same pack together. When both return, `CompanyPackState.applied_flags` equals one completed apply of that pack. No flag is missing and no flag is written twice into a torn snapshot. Do not hand-edit a flag inside this test.

Do not weaken the skip. Local pytest without `CI=1` and `DATABASE_URL` must skip both tests.

**DoD.**

- [x] Both tests skip on SQLite.
- [x] On Postgres, two different orders for one customer cannot both confirm when the limit covers only one of them. Local SQLite skips this; CI's Postgres job runs it.
- [x] The confirm race uses two order rows. It does not call `confirm_sales_order` twice on the same order. Both rows start CANCELLED so a pre-existing draft does not make both confirms fail before the lock matters. Each thread drafts its own order inside the confirm transaction.
- [x] On Postgres, two concurrent applies of the same pack leave one consistent `applied_flags` snapshot. Local SQLite skips this; CI's Postgres job runs it.
- [x] The hand-edit case stays in the existing sequential tests and is not rewritten as a race.

**Effort.** 1–2 days, and the proof is a CI run, not a local SQLite run.
