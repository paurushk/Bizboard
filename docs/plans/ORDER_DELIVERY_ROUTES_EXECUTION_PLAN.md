## 0. Rules for everyone executing this

1. **Hardening only.** No new screens beyond finishing existing ones, no new statuses, no stored fields except the one table in R7 (acknowledgements). Read-only derived fields on existing responses are allowed.
2. **Reproduce first.** For every task: write the failing test(s), see them fail for the stated reason, then fix. A finding that does not reproduce is recorded as "not reproducible" in the tracker (section 7) and its task is dropped, not forced.
3. **One task, one commit.** Message `<task-id>: <what>`. A task never mixes two releases. Money and stock tasks (T-1.1 to T-1.3, T-3.2) are separate commits with a stated rollback.
4. **Tests must be order independent.** CI runs `pytest-randomly`; each test builds its own tenant state with `tenant_a` / `tenant_b` and the helpers in `backend/tests/conftest.py`.
5. **Gates must pass before a release is merged** (section 2). Never skip a hook or loosen a check.
6. **Do not edit generated files by hand.** `docs/openapi-snapshot.json` and `web/src/api/openapi-types.ts` are regenerated by command (section 2) and committed with the change that caused them. Do not read them wholesale; grep.
7. **Permissions and company isolation are part of every task.** New endpoints get a permission class, the subscription write gate for writes, company scoping, and a row in the route isolation matrix.
8. **Stop and ask** if a task would need a new stored field, a new status value, a new document type, or changes the meaning of money or stock beyond what is written here.

## 2. Standard procedure and gates

**Per task**
1. `git switch -c <task-id>-<slug>` from the release branch.
2. Add the failing tests from the task's "Tests" line. Mark each `@pytest.mark.xfail(strict=True, reason="<finding id>")` (backend) or `it.fails` (web). Run them; confirm they fail for the stated reason.
3. Implement. Remove the xfail marks. Confirm they pass.
4. Run the task's targeted suites, then the release gates below.
5. If an API response changed, regenerate the snapshot and types (below) and commit them together.
6. Update the tracker (section 7) with commit and result.

**Commands** (from `E:\Bizboard`)

| Purpose | Command |
|---|---|
| Backend targeted tests | `cd backend && pytest tests/<file>.py -q` (use `--create-db` once after any migration; Postgres-only cases are marked `postgres`) |
| Backend full (CI parity) | `cd backend && pytest -m "not flaky_quarantine and not slow and not llm_accuracy" -q` |
| Strict invariants (CI parity) | `cd backend && INVARIANTS_STRICT=1 pytest tests/workflows/ tests/tenancy/ tests/gst/ -q` |
| Backend lint | `cd backend && ruff check .` |
| Migration check | `cd backend && python manage.py makemigrations --check --dry-run` |
| OpenAPI snapshot | `cd backend && python manage.py spectacular --format openapi-json --file ../docs/openapi-snapshot.json` then `git diff docs/openapi-snapshot.json` must be only your intended change |
| Web API types | `cd web && npm run gen:api-types` then check `git diff src/api/openapi-types.ts` |
| Web type-check | `cd web && npx tsc -b` (not `tsc -p .`) |
| Web lint | `cd web && npm run lint` (must stay at 0 errors) |
| Web tests | `cd web && npx vitest run <path>` / `npm run test:run` |
| Golden e2e | `cd web && npm run test:e2e:golden` |
| Quality registry | `python qos/tools/lint.py` |

**Release gate (all must pass):** targeted tests · full backend suite · strict invariants · `ruff` · `makemigrations --check` · OpenAPI snapshot clean · web types clean · `tsc -b` · web lint 0 errors · full Vitest · for R5 to R7 also the golden e2e specs named in the release.

**Baseline before starting (T-0.0):** the working tree currently has many uncommitted changes from earlier work. Do not start on top of them. Either commit them in their own reviewed commit or branch from a clean checkout of the agreed base, then record in the tracker: base commit, backend failing tests (expected none), web lint status, and any test already red. A red test at baseline is recorded, not "fixed along the way".
