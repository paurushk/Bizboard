### P1-T2 — Route extractor · effort L · deps P1-T1

**Corrected premise (2026-09-13):** a review of this runbook checked
`App.tsx` directly and found the public routes are **not** in a separate
location — `App.tsx:328-333` defines `/login`, `/register`,
`/forgot-password`, `/reset-password`, `/invite`, and `/pay/:token` in the
**same top-level `<Routes>` block** as everything else, simply outside the
`<ProtectedRoute>`-wrapped subtree whose nested `<Route path="...">` entries
drop their leading slash (e.g. `sales/new`, not `/sales/new`). The
extractor's real job is distinguishing **top-level absolute-path routes**
from **nested relative-path routes under the protected wrapper** (and any
further nested wrappers — settings, accounting, etc. each add their own
`<Route element={...}>` guard layer), not hunting for a second file.

**Steps**
1. `extract_routes.py` reads `web/src/App.tsx` and walks the JSX route tree
   as a state machine keyed on nesting depth: top-level `<Route path="/x">`
   → absolute route; each `<Route element={<SomeGuard/>}>` wrapper pushes a
   guard onto the stack for every route nested inside it; a nested
   `<Route path="x">` → guard-stack-prefixed absolute path. Produces
   `{path, component, guards[], route_kind: page|redirect|index}`.
   `<Navigate>` targets are tagged `redirect`, not a page.
2. Join `web/src/navigation/menu.ts` **only** to attach `nav_label`/grouping
   (locked answer to D3 — router is truth, nav is a join, not a union). A
   `menu.ts` entry with no matching router path is flagged as a mismatch
   (dead nav item or bug), never silently added as a route.
3. **Fail loud, never silently undercount** (D2): assert
   `len(routes) >= previous_committed_count` as a sanity floor (a large drop
   is almost always a broken parser); anything the state machine can't
   classify goes into an `unparsed` bucket that fails the run until a human
   resolves it, rather than being dropped.
4. Cross-reference `web/e2e/route-smoke-unauthenticated.spec.ts`'s hardcoded
   20-route list against the extractor output as a sanity check — the
   extractor must find **at least** those 20 plus everything else reachable.

**Acceptance:** `python validation/tools/extract_routes.py --count` reports a
number in the "~90+" range the review estimated (§3); spot-check 10 routes by
hand against `App.tsx`, owned by the web lead (D4); `--selftest` proves the
floor check and the `unparsed` bucket can each fail on a planted fixture.

### P1-T4 — Coverage-label computation · effort L · deps P1-T2, P1-T3

For each route/action, auto-derive a coverage label — **JOURNEY / API-ONLY /
SMOKE / FLAG-OFF / UNIT / GAP / OUT / LIM / UNMAPPED** (first 7 per review §1;
`LIM` per B7; `UNMAPPED` is new — see below) — by cross-referencing:

- `web/e2e-golden/*.spec.ts` file contents (grep for the route path or
  page-object navigation calls) → candidate `JOURNEY`.
- `web/e2e/**/*.spec.ts` for the same route with only `heading`/`Retry`/
  `axe` assertions (no business-outcome assertion) → `SMOKE`.
- `backend/tests/personas/**/*.py` + `backend/tests/workflows/*.py` hitting
  the same capability with no UI counterpart → `API-ONLY`.
- `FREEZE_SCOPE.md`'s NOT SUPPORTED list → `OUT`.
- Recurring invoices (`/sales/recurring`) and similar reachable-but-out-of-freeze
  screens → `LIM` (B7): not `OUT` (they are reachable) and not `GAP` (they
  do not deserve a journey). A `LIM` row requires only a smoke-level
  "must not silently corrupt later data" check.
- No `FREEZE_SCOPE.md` A-row exists **at all** for this route → `UNMAPPED`
  (distinct from `GAP`, which means "a capability mapping exists but no
  gating test does" — `UNMAPPED` means the capability mapping itself is
  missing; conflating the two hides which fix is actually needed. Locked
  answer to D6).
- Nothing found and a mapping exists → `GAP` (the honest default — do not
  default to a false positive).

This is necessarily heuristic (string/AST matching, not perfect semantic
understanding) — **that's fine**. The goal is a first-pass label a human
spot-checks and corrects, not a fully automated oracle. Corrections go in
**`validation/overrides.yaml`** (a separate file, keyed by route+field),
applied as a post-processing step after the heuristic pass — reusing the
exact non-destructive-merge pattern `qos/tools/merge.py` already proved out
for Q-OS (preserves human-owned fields across re-mining) rather than
inventing a new mechanism (locked answer to D5).

**Acceptance:** run against the current tree; manually verify the labels
match at least 15 rows from the review's §2 tables exactly (e.g. `/pos`
→ JOURNEY backend / thin UI per §2.3, `/sales/quick-entry` → GAP per §2.4).
**On disagreement, the generator wins for coverage-mechanics** (it checks
actual file references; the review's own §2 tables are hand-maintained and
already flagged as possibly stale, e.g. the `cross_reconcile` overclaim) —
but every disagreement still gets one line in the landing PR, never silently
resolved either way (locked answer to D4; web lead owns this spot-check per
A5).
